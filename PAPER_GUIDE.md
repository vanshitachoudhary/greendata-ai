# Getting real results for the research paper

The dashboard numbers for energy, CO2 and cost are **assumed constants**. They are fine for a demo, but they are not
results. Results must come from experiments you ran. This guide says how to produce them with `benchmark.py`.

## 1. What can be reported, and how

| Claim | Where it comes from | Status |
|---|---|---|
| Duplicate / near-duplicate / sensitive-file detection quality | `benchmark.py synthetic` (ground truth) | Measured, on synthetic data |
| Storage saved, time, rollback integrity, safety | `benchmark.py synthetic` and `real` | Measured |
| Comparison with simple baselines | `benchmark.py` (hash-only dedup, compress-all) | Measured, our own baselines |
| Energy of running the tool | CodeCarbon (`pip install codecarbon`), else CPU-time estimate | Measured only with CodeCarbon |
| Energy / CO2 / cost saved downstream | Dashboard model | **Assumed. Do not call it a result.** |

## 2. Experiment A: controlled data with ground truth

```
python benchmark.py synthetic --sizes 100,500,2000 --runs 3 --out results
```
It builds datasets that contain exact copies, near copies (1-3% of words edited), different files that only look similar
(10% edited), sensitive files, decoys that look sensitive but are not, stale files, important recent files and
incompressible files. Then it measures precision and recall, storage saved, time, safety, energy and rollback.
Output: `results/results.md` (tables), `results.csv` and `results.json` (raw, every run).
Run it on your own laptop and report your environment, which the tool records in `results.json`.

## 3. Experiment B: real datasets

Pick two or three public datasets that are folders of files (CSV, text, logs, JSON). Check each license before using it.
```
python benchmark.py real --dir path/to/dataset --runs 3 --out results_dataset1 --sample-audit 50
```
It works on a copy, so your dataset stays untouched, and measures storage saved, time, energy and whether rollback
restores every byte. There is no ground truth on real data, so open `audit_sample.csv`, check the 50 flagged files by hand
(correct: y or n), and report precision from that sample with a 95% interval (Wilson):
`p = k/n`, interval = `(p + z²/2n ± z·sqrt(p(1-p)/n + z²/4n²)) / (1 + z²/n)` with `z = 1.96`.

## 4. Energy

1. `pip install codecarbon`, then rerun A and B. Table 4 fills the "measured" column.
2. State exactly what was measured: the energy of running GreenData (scan + apply) on your machine.
3. To claim energy saved in a downstream job, measure that job yourself: run the same pipeline (for example, training a
   small model) on the original and on the optimized data under CodeCarbon, and report both energies and the accuracy.
   That is the experiment that supports the green-computing claim. The dashboard model does not.

## 5. Reporting rules

- Report mean ± standard deviation over several seeds, the number of files and the total size.
- Report the environment (Python version, OS, CPU, CodeCarbon yes/no) and the code version.
- Never mix assumed and measured values in one table. Label estimates as estimates.
- Report weaknesses that the data shows. Reviewers trust a paper that does.

## 6. Limitations to state (they are real)

- Synthetic data was generated by us, and the definition of "near duplicate" (about 1-3% of words edited) is ours.
- Phone detection is pattern based. In our decoy test almost every decoy was flagged, so sensitive-file precision was
  about 0.6 while recall was 1.0. The tool errs on the side of protecting files. Aadhaar numbers are checksum-validated.
- The tool is much slower than naive baselines on small files (pure Python near-duplicate search). Speed is a limitation.
- Access frequency is assumed (file systems do not record it). "Last used" comes from file times.
- Baselines are our own simple implementations, not third-party tools. One machine, one operating system per run.
- Compress-all saves more space than GreenData but changes every file, including protected ones, so compare it together
  with the safety table, not on storage alone.

## 7. Suggested structure for the results section

1. Setup: datasets (size, number of files, source), baselines, metrics, hardware and software.
2. Detection quality (Table 1) and what drives the errors.
3. Safety (Table 2): protected files changed by each method.
4. Storage and time (Table 3) against the baselines.
5. Energy and rollback (Table 4), measured and estimated shown separately.
6. Real datasets: counts of flagged files, hand-checked precision, storage saved.
7. Limitations (section 6).
